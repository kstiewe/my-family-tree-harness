# Agent instructions — my-family-tree-harness

You are the operator of this genealogy toolkit. The user tells you what they know about their
family; you record it, research online registers, keep the data consistent and report gaps. The
user only reads the finished tree. This file is the general manual; family-specific rules come
from the **private workspace** and override nothing here except where they add detail.

**Do the next step; don't offer it.** If you can do the next step now within these rules, do it
in the same turn instead of ending your reply with "I can …" or "Shall I …?". That covers a
search, reading an index or a scan, recording a finding, the build, updating the published outputs
and documenting a general technique. Ask the user only for what you cannot or may not do yourself:
- signing in;
- paying;
- downloading a file, unless the user has allowed downloads (record that in the private
  instructions);
- visiting an archive or a FamilySearch center;
- choosing between conflicting family accounts;
- consent to an `allow:` entry.

In the report, list as next steps only those.

## 0. Start of every session

1. The SessionStart hook prints the workspace summary and the private `INSTRUCTIONS.md`. If you do
   not see it, run `python3 scripts/workspace.py context`.
2. Talk to the user in the language the private instructions name (default: the user's language);
   reports follow `language` in `data/project.yaml`.
3. No workspace? Ask the user. New user: `python3 scripts/workspace.py init PATH --lang pl --git`,
   then `python3 scripts/workspace.py link PATH`.

## 1. Privacy — the most important rule

This repository is **public**. The workspace is **private**. Never let anything about a real
family into the repository: no names, places, parishes, dates, IDs, URLs of records or artifacts,
relationships, search results or open leads — not in code, comments, tests, examples, docs,
commit messages or file names. Examples and tests use only the fictional family in
`examples/sample-family/`.

- Family data and family-specific notes go to the workspace (`data/`, `research/`, `INSTRUCTIONS.md`).
- A general technique learned while researching goes to `sources/` or `docs/`, **rewritten with the
  fictional family** (Kowalski, Nowak, Przykładowo …) — never with the real example that taught it.
- Before writing text into the repository, check it: `python3 scripts/guard.py check < file`.
- The git hooks run the guard on every commit and push (`python3 scripts/guard.py install` once per
  clone). Never use `--no-verify`. If the guard blocks, rephrase or move the content to the
  workspace; only a generic phrase (e.g. an archive's name) may go to `allow:` in the workspace
  `privacy.yaml`, and only with the user's consent.
- Do not search online for living persons: `living: true`, or no `living` field and born less than
  100 years ago without a death date. `living: false` (death confirmed by the family, even without
  a date) lifts the block. Never log in to the user's accounts.

See docs/privacy.md for the model behind this.

## 2. Source of truth

`<workspace>/data/*.yaml` is the only source of truth; `<workspace>/output/` is generated by
`python3 scripts/build.py` and never edited by hand. After every data change run the build and fix
all errors. The data model: docs/data-format.md, machine-readable: `python3 scripts/build.py --schema`.

## 3. When the user gives you new information

**Record every clue.** Everything the user says goes into the data, also when it is uncertain
("maybe", "I think", "probably"), second-hand, contradicts what is already recorded, or seems
minor (a nickname, where someone "came from", where they lived, who moved from where, siblings):
- verbatim into `transcription` of a `type: oral` source, with `informant` (who said it, through
  whom, when);
- as content into the right person, family or place (`events` with the source, `notes`, `todo`);
- what the data model cannot hold (e.g. siblings with unknown parents) into `notes` of the
  closest person;
- a correction never deletes the earlier version — describe in `notes` what changed, when, and on
  whose account.
Leave nothing out. If something ended up only in notes, say so in your answer.

Steps:
1. Check for duplicates first: `python3 scripts/build.py --find "<surname>"` (ignores diacritics,
   includes variants; `--json` for machine-readable output).
2. Add places first (find the parish, partition, `geneteka_region` and `coords`; the parish of a
   village is in the Słownik geograficzny or in `python3 scripts/geneteka.py --parishes -w CODE`;
   coordinates come from one targeted gazetteer lookup, see `sources/gazetteers.md`, with the source
   in `notes`), then the source (a family account is `type: oral` with `informant`), finally persons
   and families.
3. Take new IDs from the "Next free IDs" line of the build (or `next_ids` in `--json`).
4. In families.yaml put a comment with the name next to every ID.
5. Mark uncertain things `confidence: probable` / `hypothesis` and give the reason in `notes`.
6. For every record, set `language` of the source — the language of the original document
   (`pl`, `la`, `de`, `ru` …; a list if mixed), e.g. Latin parish books, German civil registers
   (Standesamt), Russian records of Congress Poland after 1868. Keep transcriptions in the original
   language and spelling; put Latin, Russian and German forms of names into `variants`.
7. Run the build, fix the errors, read the new chronology warnings.
8. Answer briefly: what was added, new warnings, the 3–5 most important gaps from the gap report
   (`output/gaps.md`, Polish: `output/luki.md`).

## 4. Online research

- Read the workspace `research/log.md` first so you do not repeat searches, and the workspace's
  own research notes.
- **Local copy first.** Before opening a source online, look for it in the workspace `research/skany/`
  (`output/scans.md` lists what is saved and under which source). A source that can be checked — a scan, a
  photo, a saved page — is downloaded and saved there **as soon as it is found** (where downloads are
  allowed, see the private instructions), named after the photo or signature, and attached to its source
  with `file`. The build lists the sources still without a copy; clear that list instead of letting it grow.
  Layout: `research/skany/<archive or service>/<fonds>/<file>`.
- Read the guide of the service in `sources/` before using it, and of the region in
  `sources/regions/`. Add what you learn about a service or region there (generic, fictional
  examples) — this is how the toolkit grows. Family-specific findings (which parish IDs you used,
  where a record was) go to the workspace.
- Before searching for an ancestor whose place of birth, place of death or parents are missing, read
  the workspace `output/geography.md` (Polish: `geografia.md`; the same as JSON in `geography.json`):
  clusters of the family's places, migration trails along each line, and per ancestor a reference
  place, the parishes and family places within 25 km and where the surname occurs elsewhere. Search
  the reference parish first, then the neighbouring ones nearest first, within the estimated years.
  It is a heuristic for choosing where to search, never evidence; see docs/geography.md.
- Geneteka: `python3 scripts/geneteka.py` builds links, lists parishes and gives a surname overview;
  read result tables in a browser (the API gives scripts incomplete data — do not work around it).
- An index hit is a candidate, not a fact. Judge a match by the parents' names, the place, the age
  and the witnesses. Without a scan, at most `probable`.
- Record every finding in `sources.yaml` (scan URL, signature, transcription, `language`) and in
  `research/log.md`. Record negative results in the log too.
- No mass downloading: single, targeted queries (the scripts pause between requests).
- Use the browser for sites that need it; decline non-essential cookies.
- A scan behind a login or a bot check: never sign in or tick the check yourself. When the user asks you to
  use their own signed-in browser (through a browser extension they have connected), only read there, one
  record at a time, and stop at any check or login form. Otherwise give the user the exact link, book and
  image number, ask them to save the image into the workspace (or paste it into the chat) and read it from
  there; see `sources/metryki-genbaza.md` and `sources/familysearch.md`.
- A lead that only a paid service can settle (e.g. an Archion pass) goes into a register in the workspace `research/`: the
  book (id, signature), the record sought, what it would settle, what free indexes already give. The user buys access once
  the list is long enough; see `sources/german-sources.md`.

## 5. Data conventions (short)

- Dates in quotes: "1850-03-12", "1850", "~1850", "<1870", ">1845", "1848..1852". Gregorian; a
  Julian date from a Russian-partition record goes to `note`.
- Women: `surname` = maiden name, surnames after marriage in `married_surnames`.
- Always record ages from records (`death.age`, `marriage.husband_age` / `wife_age`).
- Latin, Russian and German forms of names and surnames in `variants`.
- From every record, also the parents' records in a child's baptism, take into the structure what it says about each
  person: an `occupation` event (value as written, date, source), a `residence` event (house number in `value`), the
  cause of death, `godparents`, `witnesses`, a `signature` event (signed / mark). The card's "At a glance" is computed
  from these fields, not from notes (docs/data-format.md).

## 6. Commands

| Command | What it does |
|---|---|
| `python3 scripts/build.py` | validate + generate outputs; prints errors, warnings, next free IDs |
| `python3 scripts/build.py --json` | the same as JSON: issues with `code`, `record`, `message`, `fix` |
| `python3 scripts/build.py --check` | validate only |
| `python3 scripts/build.py --find TEXT [--json]` | duplicate check |
| `python3 scripts/build.py --public` | HTML, map and GEDCOM without living persons |
| `python3 scripts/build.py --schema` | the data model as JSON |
| `python3 scripts/geneteka.py --help` | Geneteka links, parishes, surname overview |
| `python3 scripts/workspace.py where / context / init / link / serve` | the private workspace |
| `python3 scripts/guard.py check / scan / audit / terms / install` | privacy guard |
| `python3 -m unittest discover -s tests` | tests (fictional data only) |

## 7. Changing the application

- Code, comments, docstrings, identifiers and these instructions are in English. User-facing text
  goes through `familytree.i18n.tr("English text")` (templates: `⟦English text⟧`) and gets a
  translation in every catalog in `familytree/locales/` (the tests check coverage).
- Keep the data format backwards compatible: never require users to rewrite their data.
- Add tests for new behaviour using the sample family; run the tests and the guard before committing.
